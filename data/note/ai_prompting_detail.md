## 第1章 指示の書き方

### 大事な考え方
あいまいな言葉を足すのではなく、できたかどうかを判断できる具体的な基準に置き換える。

### 指示に入れる5つの要素

| 要素 | ✕ 悪い例 | ○ 良い例 |
| --- | --- | --- |
| タスク（何をするか） | 「この議事録について」 | 「この議事録を要約して」と動詞ではっきり言う |
| 背景と読み手 | 「要約して」 | 「来週の部内会議で配るので、初めて読む人向けにこの議事録を要約して」 |
| 形式 | 「要約して」 | 「決定事項と宿題を分けて、それぞれ3行以内で」 |
| 制約 | 指定なし | 「議事録にない日付や担当者は足さないこと」 |
| お手本 | 言葉だけで説明する | 過去のよくまとまった週報を1〜2本付ける |

- お手本は、言葉で説明しにくい基準を伝えるのに最も効く。
- ✕「もっと丁寧に」「注意深く」「もっと徹底的に」のように、あいまいな言葉を足すだけの指示。あいまいな指示にあいまいな言葉を重ねても、基準は増えない。
- ○「1行目に決定事項、担当者と期限は議事録にあるものだけ」のような判断できる基準。
- 役割の指定（「あなたはベテランの編集者です」「あなたは経理の担当者です」など）は、文体やトーンを整えるのには効く。ただし事実の正確さは上がらない。経理の担当者と書いても、存在しない勘定科目や税率を書かなくなるわけではない。

### タスクの分け方
- ○複雑な依頼は小さなステップに分けて、順番に進める。分けると効くのは次の4つの場合。
  - 種類の違う作業が混ざっている（例:問い合わせメールを種類ごとに分け、多い困りごとを整理し、よくある質問の案にする、は別々の3作業）
  - 後の作業が前の作業の結果を使う（種類分けが決まらないと困りごとの整理は始められない）
  - 途中で人が確認したい（種類分けの基準が妥当かを見てから次へ進む）
  - 一度に出すと長すぎて質が落ちる（各部分を個別に作り、最後にまとめる）
- ○分けておくと、どこで間違えたかを突き止めやすい。一度に大きく頼んで間違った結論が出ると、原因が種類分けなのか整理なのか切り分けられない。
- ✕単純な作業まで細かく分けるのは非効率。メールの宛名を直すだけの依頼を何段階にも分ける必要はない。分ける細かさは作業の複雑さに合わせる。

### 出力を見て直すとき
一度で完璧な出力が出ることはまれ。期待とどこが違うかを見つけて、その違いに合った指示を足す。

| 問題 | ○ 効く直し方 | ✕ 効かない対応 |
| --- | --- | --- |
| 一般論ばかりで具体性がない | 参照する資料を渡し、具体例の数を指定する | 「もっと具体的に」とだけ書く |
| 長すぎる・短すぎる | 文字数や項目数を数字で指定する | 「簡潔に」とだけ言う |
| トーンが読み手に合わない | 読み手を伝え、お手本の文を1つ見せる | 上位のモデルに変える |
| 形式がばらつく | 出力のテンプレートを渡す | 同じ依頼を何度も出し直す |
| 事実が間違う | 根拠の資料を渡し、資料にないことは書かせない | 「正確に書いて」と指示する |

- ✕指示があいまいなままモデルだけ変える。指示があいまいなら、どのモデルでも期待を推測するしかない。先にプロンプトを直すのが正しい順番。

### 作業の種類ごとのやり方

| 種類 | 目的 | ○ 効くやり方 |
| --- | --- | --- |
| 分析 | 与えた情報から示唆を引き出す | 見る観点と評価の軸を伝える。根拠の箇所を引用させる。資料にない推測はさせない |
| 調査 | 知らない情報を集めて整理する | 範囲と期間を絞る。出典を必ず付けさせる。出典をたどれる手段を使う |
| 文章作成 | 読ませる文章を作る | 読み手、目的、トーン、長さ、構成を指定する。過去の良い例を見せるのが最も効く |
| アイデア出し | 選択肢を広げる | 数を多めに頼む。その場では評価せず量を出させ、後で絞る。条件を変えて視点を変える |

- アイデア出しでは、確かめていない多様な案が歓迎される。分析では、根拠のない推測は欠点になる。同じ「推測を含む出力」でも、何のための作業かで良し悪しが逆になる。
- アイデア出しで出た案も、実行すると決める前には確かめる必要がある。

## 第2章 出力の評価と確認

### 大事な考え方
AIの出力は疑ってかかり、AIとは別の情報源で確かめてから使う。

### 評価の2つの軸

| 軸 | 確かめること | よくある失敗 |
| --- | --- | --- |
| 正確性 | 書いてあることが事実か（数値、引用、固有名詞、日付） | 存在しない条文番号、実在しない統計、間違った社名 |
| 完全性 | 必要なことが漏れなく入っているか、依頼の全項目に答えているか | 3つ聞いたのに2つしか答えていない、大事な例外条項が抜けている |

- 「間違っていない」と「十分である」は別。漏れのほうが間違いより見つけにくい。書いてあることが全部正しくても、決定的な条件が抜けていれば判断を誤る。
- ✕出力を読むだけで確認を終える。
- ○元の依頼と見比べて、答えていない項目がないか探す。

### もっともらしいウソ（ハルシネーション）
AIは「次に来る自然な言葉」を予測する仕組みで、事実を照らし合わせる仕組みを持っていない。だから、もっともらしいウソは不具合ではなく仕組み上起きる。

起きやすい場面
- 条文番号、統計、日付、価格、URL、論文名、人名などの細かい情報。具体的なほど疑う。
- 資料に書いていないことを聞いたとき。空欄より、もっともらしい値で埋めがち。
- 専門性の高い分野や、最近の出来事。
- 前提が間違っている質問。「就業規則の第8条にある在宅勤務の条件を説明して」と聞くと、第8条が在宅勤務の話でなくても説明を作ってしまうことがある。

- ✕「AIに自信の度合いを聞いて、高ければ送る」。自分で答えた自信の度合いは、内容の正しさではなく文章の作りやすさを表しているだけ。
- ○AIが断定的に、詳しく、自信ありげに書いていても、正しい証拠にはならないと考える。

誤りが起きたときの影響の大きさで、確認の深さを変える。

| 影響 | 例 | 必要な確認 |
| --- | --- | --- |
| 高 | 法令や規制の解釈、財務の数値、医療や安全、外部に公開する文書、契約 | 元の情報源との照合が必須。さらに資格のある人が確認する |
| 中 | 社内報告書、提案の根拠データ、顧客への説明 | 主な事実と数値を出典で確認する |
| 低 | アイデア出し、下書きの構成案、社内メモの整形 | 通して読み、明らかな誤りがないか見る |

### 矛盾と偏り
矛盾は長い出力ほど起きやすい。
- 本文の数値と、要約や表や結論の数値が違う
- 前半で「増えている」、後半で「減っている」と書く
- 合計と内訳の足し算が合わない

- ○数値を扱う出力は、足し算と引き算を必ず確かめる。最も手間が少なく効果の大きい確認。

偏りが入る経路

| 経路 | 内容 |
| --- | --- |
| 学習データ | 社会の思い込みが出る（職種と性別の結びつけ、特定の地域や属性への偏った評価） |
| 渡した資料 | 資料そのものが偏っている。自社に有利な事例だけ渡せば、結論も自社寄りになる |
| 質問の仕方 | 「なぜうまくいったのか」と聞けば、失敗の可能性は検討されない。結論を前提にした問いが結論を作る |
| 材料の選び方 | 反対の材料があるのに、支える材料だけがまとめられる |

| ✕ 悪い聞き方 | ○ 良い聞き方 |
| --- | --- |
| 「この改善がうまくいった理由は？」 | 「この改善でうまくいった点と、うまくいかなかった点を同じ数ずつ挙げて」 |

反対の材料をはっきり求めるのが、偏りを防ぐ最も簡単で効く方法。

### 事実を確かめる方法
AIとは別の情報源で確かめるのが原則。AIの出力を同じAIに確認させても、独立した確認にならない。

| 方法 | 内容 | 向いている場面 |
| --- | --- | --- |
| 元の情報源と照合 | 原文、公式サイト、社内の正式データに当たる | 数値、引用、条文。最も確実 |
| 出典を示させる | 主張ごとに根拠の箇所を示させ、人がそこだけ確認する | 長い分析、調査結果 |
| 資料内に限る | 「資料にあることだけで答え、ない場合は『記載なし』と書く」と指示する | 資料をもとにした抜き出しや要約 |
| 計算し直す | 合計、割合、差を自分で計算し直す | 数値を含む出力すべて |
| 専門家に確認 | その分野の資格のある人に見てもらう | 法務、医療、財務、安全 |

- ✕同じAIに「これは正しいですか」と聞き直す。自信を持って「正しい」と答えたり、同じウソを繰り返したりする。聞き直しは見落としに気づくきっかけにはなるが、事実確認の代わりにはならない。
- ○外部の信頼できる情報源で確かめる。

### 人の確認が必要な場面
次のどれかに当てはまるときは、人が確認する。
- 取り消しが難しく影響が大きい（外部公開、契約、送金、人事の判断）
- 法律や規制が関わる（法令の解釈、コンプライアンス報告、当局への提出物）
- 人についての判断（採用、評価、与信、懲戒）。最後の説明責任は必ず人が持つ
- 確かめられない数値や事実が入っている
- 専門的な判断が必要（医療、法律、税務、安全）
- 社内ルールで人の確認が決まっている

| ✕ 悪い対応 | ○ 良い対応 |
| --- | --- |
| 上司に転送して承認ボタンを押してもらうだけ | 誤りを見つけられる知識のある人が、根拠の資料と照らし合わせて確認する |

### 読み手と出力形式

| 読み手 | ○ 合わせる内容 | ✕ 避けること |
| --- | --- | --- |
| 経営層 | 結論を先に。影響、選択肢、判断に要る数字 | 技術の細かい話、長い経緯 |
| 現場の担当者 | 手順、条件による分かれ道、具体的な操作 | 方針だけの抽象的な話 |
| 顧客や社外 | やさしい言葉、正確さ、社内用語を使わない | 社内の略語、決まっていない情報、言い切りすぎ |
| 法務や財務 | 根拠と原文、正確な用語 | 要約して条件を省くこと |

出力形式は、その成果物をこの先どう使うかで選ぶ。

| 形式 | 向いている場面 |
| --- | --- |
| 会話の中に表示 | 短い回答、その場で読んで終わるもの、判断の材料 |
| Artifacts（会話とは別に作る文書） | 何度も直す長い文書、共有や再利用する文書、コード、企画書 |
| 表、箇条書き、CSV | 別のツールに取り込む、件数が多い、比べる、集計や並べ替えをする |

## 第3章 機能とモデルの選び方

### 大事な考え方
いつも最高性能のものを選ぶのではなく、作業に合った機能とモデルを選ぶ。

### 機能の使い分け
選ぶときは、一度きりか繰り返しか、短いか長いか、根拠をたどる必要があるか、の3つを見る。

| 機能 | 向いている場面 | 選ぶ目安 |
| --- | --- | --- |
| チャット | 一度きりの質問、短い下書き、その場の相談 | 「今回だけ」「すぐ答えがほしい」 |
| Projects | 同じ資料とルールで繰り返す業務 | 「毎週やっている」「毎回同じ説明を貼っている」「チームで質をそろえたい」 |
| リサーチモード | 複数の情報源から調べて、出典付きで整理する | 「調べる必要がある」「根拠を示す必要がある」 |
| Artifacts | 長い成果物を何度も直し、そのまま共有や再利用する | 「何度も直す」「文書として渡す」 |

- ✕毎回チャットに同じ背景資料や前提を貼り直す。担当者によって出力の質がばらつく。
- ○繰り返す作業は、Projectsに指示と資料を登録しておく。

### モデルの選び方

| モデル | 強み | 向いている作業 |
| --- | --- | --- |
| Haiku | いちばん速くて安い | 単純で決まった作業を大量に（短い返信、分類、タグ付け、表記をそろえる）。品質より速度とコストを優先するとき |
| Sonnet | バランスがよい | ふだんの仕事の主力（報告書の下書き、要約、通常の分析）。迷ったらこれ |
| Opus | 考える力がいちばん高い | 複雑な判断、複数の資料をまとめる、難しい文書を読む、戦略の分析 |

- ✕「品質を最大にするため、いつも最上位のモデルを使う」。お金と待ち時間のムダ。
- ✕「コストを下げるため、全部いちばん軽いモデルにする」。複雑な作業では力が足りない。
- ○作業の中身に合わせてモデルを選ぶ。

### 品質・速度・コストのバランス
3つを同時に最大にはできない。その作業で何がいちばん大事かを先に決める。

| 状況 | 優先すること | 選び方 |
| --- | --- | --- |
| 毎日大量に届く問い合わせへの定型の返信案 | 速度とコスト | 軽いモデル。決まった文なら品質の差は小さい |
| 年に一度の事業計画の見直し | 品質 | 上位のモデル。件数が少なく、誤りの代償が大きい |
| 顧客対応中にその場で調べる | 速度 | 軽いモデルか中くらいのモデル。待たせないことが価値 |
| 複雑な契約書の条項の比較 | 品質 | 上位のモデルに加えて、人が確認する |

- 件数が多く、1件ごとの影響が小さい作業は軽いモデル。
- 件数が少なく、1件ごとの影響が大きい作業は上位のモデル。

### 長い会話と記憶の扱い
会話が長くなると、最初に伝えた指示や資料が反映されにくくなる。

| やり方 | 使う場面 | 気をつけること |
| --- | --- | --- |
| 新しい会話を始める | 話題が変わったとき。前の話に引きずられて出力が悪くなったとき | 必要な前提は改めて伝える |
| 要約して引き継ぐ | 長い会話の続きを新しい会話で進めたいとき | 要約すると情報が落ちるので、決まったことと条件ははっきり残す |
| Projectsに登録する | これからも繰り返し使う前提、ルール、資料 | 会話の中ではなく、Projectsの指示や資料に置く |

- ✕その案件だけの一時的な話までProjectsに登録する。
- ○何度も説明し直している情報だけを登録する。
- ○メモリ機能に何が記憶されているかを把握し、古いものや要らないものは消す。この管理は使う人の責任。

## 第4章 業務への組み込み

### 大事な考え方
AIを入れることは、人を仕事から外すことではない。AIが下書きや整理や候補出しをして、人が確認と決定をする。

### まず業務の課題を整理する
- ✕先にツールや技術を決める。
- ○先に業務の課題をはっきりさせる。

確かめること
- 誰のどの作業が、なぜ困っているか（時間がかかる、品質がばらつく、特定の人しかできない）
- 今どうやっているか。今のやり方を知らないと、改善か改悪か判断できない
- 成功をどう測るか（所要時間、手戻りの割合、品質の基準）。測れない改善は評価できない
- 制約（データの機密性、既存のシステム、規制、承認の流れ）
- 最後の責任を誰が持つか

| AIに向いている作業 | AIに向いていない作業 |
| --- | --- |
| 文章を作る、要約する、書き換える、翻訳する | 必ず一つの正解が出ないと困る計算や記録 |
| 大量の文章を整理して分類する | 厳しい監査記録が必要な基幹の処理 |
| 下書きを作る、選択肢を洗い出す | 人が説明の責任を持つ最終判断 |
| 資料を読む手助け、論点の整理 | 確かめようのない事実を作ること |

- 「自動化」と「無人化」は違う。
- ✕影響が大きい工程で、人の確認を外す。
- ○AIが下書きや候補を出し、人が確認して決める。

### 考える作業にも使う

| 使い道 | 使い方 |
| --- | --- |
| 調査 | 選択肢の洗い出し、比べる軸づくり、他社事例の整理。出典を必ず付けさせ、大事な事実は確かめる |
| 計画 | 作業を分ける、作業どうしのつながりの整理、リスクの洗い出し、スケジュール案 |
| 手順の改善 | 今の手順を説明して、詰まっている所やムダな重なりを指摘させ、改善案を出させる |

今の手順をAIに説明していると、自分でも説明できない工程や、理由の分からない習慣が見つかる。改善は、今のやり方を見える形にすることから始まる。

### 小さく始めて広げる
1. 1つのチームと1つの業務で、少ない件数から試す
2. 今のやり方と、時間、品質、手戻りを比べる
3. 指示、資料、確認の手順を直す
4. 事前に決めた基準を満たしたら広げる
5. 広げたあとも品質を見続ける。気づいたことは次の改善に回す

- ✕全社で一斉に入れる。問題が起きると全社が同時に困る。
- ✕完璧になるまで出さない。これでは永久に出せない。
- ○成功の基準を先に決めて、段階的に広げる。

### 今の業務への組み込み方

| やり方 | 内容 | 向いている場面 |
| --- | --- | --- |
| 拡張 | 今の手順のまま、一部の作業をAIに任せる | 今の手順は妥当で、単に負担が大きいとき。リスクが低く早く入れられる |
| 作り直し | 工程そのものを組み替える | 今の手順に仕組みとしてのムダがあるとき。効果は大きいが、変更の管理と関係者の合意が必要 |

組み込むときに必ず決めること
- どの工程をAIが担い、どの工程を人が担うか
- 誰が、何を基準に、いつ確認するか
- うまくいかないとき、誰にどう回すか
- 扱うデータを会社のルール上使ってよいか

### 関係者への伝え方

| ✕ 悪い伝え方 | ○ 良い伝え方 |
| --- | --- |
| 「AIが全部やってくれます」 | 「下書きの時間が短くなり、確認は今まで通り担当者が行います」 |
| 「100%正確です」 | 「事実の確認が必要な出力なので、確認の手順を組み込んでいます」 |
| 「人を減らせます」 | 「同じ人数でより多くの案件を扱えます（試行で何%短縮したかを添える）」 |
| 技術の仕組みばかり説明する | 業務の成果と、その測り方で話す |

- 大げさな約束も、専門用語でけむに巻く説明も、どちらも良くない。
- 「誤りゼロを保証して」と頼まれても、保証はできないと正直に伝える。そのうえで、測れる品質の目標と人の確認手順を示す。守れない約束は、あとで信頼を失う原因になる。

## 第5章 設定と資料の管理

### 大事な考え方
「どう振る舞うか」はカスタム指示に、「何を参照するか」はナレッジに置く。作ったあとも手入れを続ける。

### Projectsの2つの設定

| 設定 | 中身 | 置くもの |
| --- | --- | --- |
| カスタム指示 | プロジェクト内のすべての会話で守られるルール | 役割、トーン、出力形式、制約、禁止事項、判断の基準 |
| ナレッジ | プロジェクトが参照する資料 | ブランドガイドライン、テンプレート、製品仕様、過去の良い例、用語集 |

- ブランドガイドラインの文書そのものはナレッジに置く。「必ずブランドガイドラインの用語に従うこと」という指示はカスタム指示に書く。両方そろって初めて効く。
- 指示の例: 「商品の価格や納期は作らず、ナレッジの資料にあるものだけを使う」

Projectsにするとよい業務
- 週次や月次など、繰り返し発生する
- 毎回同じ資料をアップロードしている
- 複数の人が同じ作業をしていて、品質がばらつく
- 決まった形の文書を作り続ける

### カスタム指示の書き方
カスタム指示は、一つひとつの依頼より上の、全体のルール。

| ○ 書くこと | ✕ 書かないこと |
| --- | --- |
| 毎回守るルール | その日だけの依頼 |
| 出力のテンプレート | 個別の案件の名前や数値 |
| 使ってよい言葉と使わない言葉、用語の統一 | パスワードやAPIキーなどの秘密情報 |
| 迷ったときの基本方針 | 締切や担当者など、よく変わる情報 |
| 「資料にないことは書かない」などの制約 | お互いに矛盾するルール |

- ✕指示に大量の内容を詰め込む。一つひとつのルールが埋もれて守られにくくなる。毎回全部読ませると、コストも上がり注意も散る。
- ○指示は短いルールに絞り、量の多い情報はナレッジに置く。

### ナレッジの管理
ナレッジは置いたら終わりではない。古い資料は間違った出力の原因になる。
- どの版が入っているか分かるようにする。古い版は消すか、使える期間を書いておく
- 元の資料が改訂されたら、ナレッジも更新する決まりにしておく
- 関係の薄い資料は入れない。正確さが上がるどころか、出力がぼやける
- アップロードする前に、入れてよいデータか確かめる

### コネクタ（Google DriveやGmailなどとの接続）
つないだ範囲が、そのままAIの参照する範囲になる。

| 観点 | 考えること |
| --- | --- |
| 範囲を最小にする | 業務に必要なフォルダとアカウントだけをつなぐ。「全部つないでおけば便利」は誤り |
| 見える権限の引き継ぎ | つないだ本人が見られる情報が対象になる。他人の機密情報が入っていないか確かめる |
| 会社のルール | コネクタを使うこと自体が認められているか確かめる |
| 新しさ | つないだ先が更新されると参照内容も変わる。アップロードした資料との重なりや食い違いに注意 |

| 資料の性質 | 置き方 |
| --- | --- |
| あまり変わらない資料（ガイドライン、テンプレート） | ナレッジにアップロードする |
| よく更新され、いつも最新を見たい情報 | コネクタでつなぐ（範囲は最小限にする） |

### 設定を保ち続ける
組織のルール、資料、業務の手順が変わるので、設定は古くなっていく。
- ✕作った人が作りっぱなしにする。
- ○設定を手入れする担当者を決めておく。

担当者がやること
- 指示とナレッジが今の状況に合っているか、定期的に見直す
- 元のルールや資料が変わったら、設定も変える決まりにしておく
- 出力の品質が急に落ちたら、まず設定と資料の変更履歴を確かめる
- 要らなくなった古い指示を残さない。矛盾の原因になる

## 第6章 ルールと責任ある使い方

### 大事な考え方
「できるか」ではなく「してよいか」で考える。決めるのは自分の判断ではなく会社のルール。迷ったら実行する前に確認する。

### 使ってよい場面と、慎重にすべき場面

| ○ ふつうは使ってよい | ✕ 慎重に考える（多くは使わない） |
| --- | --- |
| 文書の下書き、要約、整形 | 採用、解雇、与信など、人についての最終判断をAIに任せる |
| アイデア出し、論点の整理 | 医療の診断、法律や投資の助言など、資格のある専門家の判断の代わり |
| 調査の手伝い（確かめる前提） | 確かめずに事実として外部に出す |
| 社内資料を読む手助け | 機密データを承認なしで入れる |
| 翻訳や言い換えの手伝い | 個人を評価したり監視したりする目的 |

- 人についての判断は、AIが材料を整理し、資格のある人が決めて、その人が責任を持つ形にする。
- ✕AIに決めさせる。
- ✕心配だからAIを一切使わない。これは行きすぎ。

### 機密データと個人情報
判断の順番
1. 何のデータか確かめる（個人情報か、規制の対象か）
2. 会社のルールで使ってよいか確かめる
3. 名前や番号など、人を特定できる情報を消すか、匿名にする
4. 実行する

- ルールではっきり禁止されているときは、実行しないか、正式な承認をもらう。
- ただし匿名にすれば使えるなら、作業そのものをあきらめる必要はない。
- 基本は、作業に要らない情報は渡さないこと。問い合わせの件数を数えるのに、顧客の名前や電話番号はたいてい要らない。
- ✕「社内で使うだけだから、そのままアップロードしてよい」。社内だけで使う場合でも、規制対象の個人データは守る対象。
- ✕「AIに覚えないよう指示する」。これでは会社の管理ルールを満たさない。
- ○人を特定できる情報を消すか匿名にしてから使う。

### 会社のルールに従う

| 場面 | とる行動 |
| --- | --- |
| ルールではっきり禁止されている | 実行しない。必要なら正式に例外の承認を求める |
| ルールがあいまい、または書かれていない | 実行する前に法務、セキュリティ、コンプライアンスの担当に確認する |
| 技術的に複雑な連携が必要 | 専門の設計者や開発者に相談する |
| ルールが現場に合っていない | 勝手に破らず、正式な手続きで見直しを提案する |

- ✕実行してから報告する。外部公開、データのアップロード、顧客への送信など、取り消せない行為では事後報告は管理として意味がない。
- ○実行する前に確認する。

### 倫理面で気をつけること

| 観点 | 気をつけること |
| --- | --- |
| 透明性 | AIが関わったことを、必要に応じて伝える（顧客向け、審査、学術など） |
| 公平性 | 人を評価して選ぶ用途では、属性による偏りがないか確かめ、見続ける |
| 説明責任 | 「AIがそう言ったから」は理由にならない。最後の責任は人が持つ |
| 知的財産 | 他人の著作物の扱いに注意する。生成物を自分の作品として扱ってよいか確かめる |
| 悪用の防止 | ウソの情報づくり、なりすまし、人をだます目的では使わない |

## 第7章 うまくいかないときの直し方

### 大事な考え方
うまくいかなくなったら、まず何が変わったかを調べる。原因を突き止めてから、1つずつ直す。

### 原因を調べる順番
「昨日まではうまくいっていたのに」というときは、変わっていないものより、変わったものを先に疑う。

| 順番 | 確かめること |
| --- | --- |
| ① 入力 | 資料を差し替えたか、データの種類や形式が変わったか、依頼文を変えたか |
| ② 設定 | カスタム指示を直したか、ナレッジを足したり消したりしたか、コネクタを変えたか |
| ③ 使い方 | 会話が長くなっていないか、別の話題が混ざっていないか、担当者が変わっていないか |
| ④ その他 | ①〜③で説明がつかないときに初めて、モデルや製品の変化を考える |

- ✕まず「モデルの性能が落ちた」と考えて、ツールを乗り換える。実際は入力、設定、使い方の変化が原因であることがずっと多い。
- ○入力、設定、使い方の変化から先に確かめる。

### 症状ごとの直し方

| 症状 | 考えられる原因 | 直し方 |
| --- | --- | --- |
| 一般論ばかりで具体性がない | 背景や資料が足りない | 読み手、目的、資料を渡す（第1章） |
| 資料にないことが混ざる | 空いているところを埋めようとする | 「資料にあることだけ」「ない場合は記載なしと書く」と指示する（第2章） |
| 形式が毎回ばらつく | 形式を指定していない、担当者ごとに違う | テンプレートを渡す。Projectsで統一する（第5章） |
| 途中から話がかみ合わない | 会話が長すぎる、話題が混ざっている | 新しい会話を始める。要約して引き継ぐ（第3章） |
| 古い情報を答える | ナレッジやメモリが古い | 資料と記憶を新しくする（第5章） |
| 指示どおりに動かない | 指示が矛盾している、長すぎる | 矛盾をなくし、短いルールに整理する（第5章） |
| 遅い、お金がかかる | 作業に対してモデルが高性能すぎる | 作業に合ったモデルに変える（第3章） |

### 一度に変えるのは1つだけ
- ✕プロンプト、モデル、資料、指示をまとめて変える。直っても、どれが効いたか分からない。次に問題が起きたとき、再現も調整もできない。
- ○1つ変えて結果を見てから、次を変える。原因を突き止めてから直す。

### 繰り返す手間を仕組みでなくす

| 繰り返している手間 | ○ 仕組みでの解決 |
| --- | --- |
| 毎回同じ直しをしている | 直す内容をカスタム指示に入れる |
| 毎回同じ資料を貼っている | ナレッジに置く |
| 担当者によって品質が違う | Projectsで前提をそろえる |
| 単純な作業に高いモデルを使っている | モデルを見直す |
| 確認に時間がかかりすぎる | 出典を示させて、確認する箇所を絞る |
